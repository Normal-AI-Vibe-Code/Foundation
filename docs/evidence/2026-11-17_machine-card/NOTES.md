## The k3s recipe, tried on Kiri first

A probe on Kiri 0.1.18 (cgroup v2, a shared WSL2 kernel) before building: k3s's server **exits without `Privileged`** (`failed to evacuate root cgroup: mkdir /sys/fs/cgroup/init: read-only file system`); with it, a server and an agent on a user-defined bridge network came up Ready (the agent joined `https://<server>:6443` by name), pods ran on both, `kubectl exec` and logs worked, and a Windows kubectl reached it through the published port. Tmpfs for /run is optional. Kiri's exec stream never ends by itself (Foundation's `execRaw` already polls), and `k3s kubectl` fails through exec where `kubectl` works.

## Not done, not verified

- **The desktop app's window wasn't driven**: the new head, the window of its own, Today's buttons in the real title bar.
- **A real public link wasn't opened**: cloudflared isn't on this computer and Foundation doesn't install it (`winget install --id Cloudflare.cloudflared`). The plumbing ran with a stand-in.
- **The Foundation link rewrites only HTML attributes**; an app that builds root-relative URLs in script needs its base. From another computer it needs this server reachable there (the desktop app's server listens on 127.0.0.1).
- **Functions run only on a person's press**; nothing runs one as new pictures arrive, and agents can't call one yet.
- **Kubernetes on Docker Desktop** wasn't tried; nodes are privileged by necessity.
- A node's card offers no Desktop (the k3s image has no package manager for one).
